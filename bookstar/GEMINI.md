## What This Project Is

A marketplace mini-app running inside the **Telebirr Superapp** (Ethiopia's leading mobile money superapp by Ethio Telecom).

It connects two user types:

- **Exam Sharers** — people with knowledge, past papers, or study experience who want to earn extra income
- **Exam Takers** — students actively preparing for an exam who need help

The platform sits in the middle: when a transaction completes, it takes a percentage cut from what the Taker pays the Sharer. All payments go through the **Telebirr native payment API** — no third-party gateways.

**Team size:** 2 developers. MVP-first approach. No over-engineering.

## Tech Stack

| Layer      | Choice                    | Reason                                                        |
|------------|---------------------------|---------------------------------------------------------------|
| Runtime    | Node.js                   | JS consistency across the stack, strong ecosystem             |
| Framework  | Express.js                | Lightweight, flexible, widely understood                      |
| Database   | PostgreSQL                | ACID compliance is non-negotiable for financial transactions   |
| ORM        | Prisma                    | Type-safe queries, clean migrations, excellent DX             |
| Validation | Zod                       | Schema-first request validation before anything hits the DB   |
| Auth       | JWT                       | Stateless, works well with REST APIs                          |
| Platform   | Telebirr Superapp Mini-App| Native payments, Ethiopian market reach                       |

**Do not suggest:**
- Python / FastAPI (not the chosen stack)
- MongoDB (PostgreSQL is locked in)
- Microservices architecture (2-person team, MVP phase)
- Third-party payment gateways that bypass Telebirr

## Core Business Logic

### 1. User Onboarding
- Users register as **Sharer**, **Taker**, or **both**
- Profile includes: name, subjects, exam types (e.g. EUEE, university CGPA exams, professional certifications)
- Linked to their Telebirr account for payment identity

### 2. Listings (Sharers)
- Sharers create listings: subject, exam type, price, short description
- Listings have statuses: `draft`, `active`, `paused`, `closed`

### 3. Discovery (Takers)
- Takers browse or search listings by subject, exam type, or price range
- Filter by rating, price, exam type

### 4. Transaction Flow
```
Taker initiates payment
       ↓
Telebirr holds funds
       ↓
Sharer fulfills (delivers material / session)
       ↓
Taker confirms receipt
       ↓
Platform releases (amount - platform_cut) → Sharer
Platform keeps platform_cut
```

### 5. Review System
- After a completed transaction, Taker rates the Sharer (1–5 stars + optional comment)
- Ratings are public and shown on Sharer profile listings

## Database Entities

```sql
users
  id, telebirr_id, name, email, role (sharer | taker | both),
  rating_avg, created_at, updated_at

listings
  id, sharer_id (→ users), subject, exam_type, price,
  description, status, created_at, updated_at

transactions
  id, listing_id (→ listings), taker_id (→ users),
  amount, platform_cut, net_to_sharer,
  status (pending | completed | disputed | refunded),
  telebirr_ref, created_at, updated_at

reviews
  id, transaction_id (→ transactions), reviewer_id (→ users),
  rating (1–5), comment, created_at
```

## API Conventions

- **Base URL:** `/api/v1/`
- **Auth:** `Authorization: Bearer <jwt>` on all protected routes
- **Response shape (always):**
  ```json
  {
    "success": true,
    "data": {},
    "message": "human-readable string"
  }
  ```
- **Error shape:**
  ```json
  {
    "success": false,
    "error": "VALIDATION_ERROR",
    "message": "price must be a positive number"
  }
  ```
- Use standard HTTP status codes: `200`, `201`, `400`, `401`, `403`, `404`, `500`

## Dev Conventions

- `async/await` everywhere — no raw callbacks
- All request bodies validated with Zod before hitting controllers
- Never hardcode secrets — everything goes in `.env`
- Prisma is the only way to interact with the DB — no raw SQL unless absolutely necessary
- Migrations only via `npx prisma migrate dev`
- Commit message prefixes: `feat:` `fix:` `refactor:` `chore:` `docs:`
- One PR per feature — keep diffs small and reviewable

---

## Telebirr Mini-App Constraints

- The frontend must use the Telebirr Mini-App SDK / framework (check Ethio Telecom developer docs for the supported stack)
- All payment initiation and callbacks go through Telebirr's native payment API
- User identity may be available natively through the Telebirr session — check if the SDK exposes a user token that can replace or supplement JWT
- The app runs in a sandboxed mini-app environment — test on the actual Telebirr sandbox before assuming browser APIs work
